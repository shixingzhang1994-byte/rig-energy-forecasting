# Project Checkpoint

从“项目负责人”和“论文审稿人”两个角度审计当前项目，建立一个保守、可追溯的阶段结论。完成 `PROJECT_STATUS.md` 更新后立即停止。

## 不可越过的边界

- 不修改代码、配置、数据、论文、实验产物或 Git 历史。
- 不新增功能、模型、模块、指标、数据集或文档。
- 不启动训练、测试、基准、仿真、重算或任何新实验；不得为了补齐证据而运行缺失单元。
- 唯一允许修改的文件是项目根目录的 `PROJECT_STATUS.md`。
- 只提出可删除或应停止的工作，不实际删除、移动、重命名或归档文件。
- 不改变已冻结的数据、参数、种子、门槛、统计口径、实验总体和研究边界。

## 审计输入

按需读取，避免把历史流水账全部加载进状态文件：

1. 根目录 `AGENTS.md` 和 `PROJECT_STATUS.md`。
2. 根目录与代码仓 README、当前论文状态/claims matrix。
3. 核心代码入口、冻结配置和与当前结论直接相关的测试代码。
4. V24、V27、V28 等关键实验的机器可读结果、完整性清单和负面/失败记录。
5. 必要的 Git 状态、差异摘要和最近提交；若根目录不受 Git 管理，也要明确记录。

不得仅依据 README 的二手摘要认定实验已经通过。文档与冻结机器可读产物冲突时，以冻结产物为证据并在状态中记录冲突；无法判定时标为证据不足。

## 审计方法

先明确本次审计目标与验收条件，然后完成以下判断：

1. 说明项目真正完成到哪个版本和阶段，不沿用乐观标签。
2. 分开列示：
   - 已实现：代码或流程存在；
   - 已测试：有可核对的测试记录；
   - 已运行：存在对应实验产物；
   - 已验证：冻结协议、完整性检查和结果足以支持限定结论；
   - 未验证：只有实现、内部仿真或跨域观测，缺少目标证据。
3. 从项目负责人角度检查范围、版本、冻结规则、复现路径、未闭环任务和资源浪费。
4. 从论文审稿人角度检查主张—证据对应、外部有效性、统计总体、负面结果、复现性和过度外推。
5. 找出最多 5 个会改变下一阶段决策的关键问题，按严重性排序。
6. 指出可以删除、归档或停止的无效工作；默认优先“停止继续投入”，不得直接删除证据。
7. 逐项判断当前实验是否真正支撑项目/论文结论，并保留仿真、公开真实观测、目标现场/HIL、部署证据之间的边界。

## 更新 `PROJECT_STATUS.md`

保持该文件简洁，只维护：项目最终目标、当前版本/阶段、已完成内容、当前问题、未解决问题、关键风险、冻结内容、证据支持/不足的结论，以及下一步任务。

- 不写执行过程、命令记录或历史流水账。
- 数字结论必须能追溯到冻结配置或机器可读结果；注明本轮是否实际复核。
- 最终只保留最多 3 个下一阶段优先任务，并说明各自解决的问题。
- 更新后立即停止，不执行任何优先任务。

## 完成条件

- 当前完成度没有把“已实现”误写成“已验证”。
- 最多 5 个关键问题和无效/停止项已识别。
- 论文核心主张均被判定为“已支持、部分支持或证据不足”。
- `PROJECT_STATUS.md` 已更新且下一步不超过 3 项。
- 除 `PROJECT_STATUS.md` 外没有产生任何项目修改或新实验产物。
